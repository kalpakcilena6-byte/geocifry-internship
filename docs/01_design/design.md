# Проектирование сервиса каталога шаблонов 'design.md'

## 1. Описание сервиса, то как мы сами это видим

Сервис предназначен для хранения шаблонов документов в форматах '.odt' и '.ott' также ведение их неизменяемой истории версий. 

**Основные принципы работы:**
1. Каждый шаблон имеет постоянный строковый идентификатор `template_id` (например, `notice`), который не зависит от имени загружаемого файла.
2. При каждой успешной загрузке файла сервис вызывает модуль `template_parser.py`, извлекающий текст документа, список подстановочных полей (например, `{NAME}`, `{DATE}`), формат, размер и контрольную сумму SHA-256.
3. Бинарные файлы сохраняются в файловом хранилище сервиса, а метаданные шаблонов, история версий и пути к файлам записываются в PostgreSQL.
4. Версии нумеруются последовательно (`1.0`, `1.1`, ..., `1.9`, `1.10`) и являются неизменяемыми (immutable): загрузка новой редакции не затирает предыдущие версии и их файлы, а при ошибке разбора файла новая версия не создаётся.


## 2. Модель данных и проектирование БД

Схема базы данных спроектирована в третьей нормальной форме (3НФ) и состоит из двух таблиц со связью `1 : 1..N` (у каждого шаблона существует минимум одна версия, создаваемая в момент первой загрузки).

Посмотреть на схемы можно в папке (ВЫПОЛНЕНИЕ ТЗ). Прикреплено два файла в формате draw.io и соответственно в .png.


### 2.1. Таблица `templates`
** Для чего:** Она хранит постоянную карточку шаблона (его уникальный идентификатор каталоге и дату первичной регистрации).

| Поле | Тип PostgreSQL | Обязательность | Ограничения и значения по умолчанию | Описание |
| :--- | :--- | :--- | :--- | :--- |
| `template_id` | `text` | `NOT NULL` (через `PK`) | `PRIMARY KEY` | Постоянный строковый идентификатор шаблона (например, `notice`) |
| `created_at` | `timestamptz` | `NOT NULL` | `DEFAULT current_timestamp` | Дата и время создания шаблона в UTC |

* **Первичный ключ:** `PRIMARY KEY (template_id)` — определяет шаблон в каталоге.
* **Внешние ключи:** отсутствуют.
* **Ограничения уникальности:** уникальность `template_id` обеспечивается первичным ключом.


### 2.2. Таблица `template_versions`
**Назначение:** Хранит неизменяемую историю версий каждого шаблона, метаданные загруженного файла, ссылку на файл в хранилище и результаты разбора из `template_parser.py`.

| Поле | Тип PostgreSQL | Обязательность | Ограничения и значения по умолчанию | Описание |
| :--- | :--- | :--- | :--- | :--- |
| `template_id` | `text` | `NOT NULL` (через `PK`) | `PK`, `FK -> templates(template_id)` | Идентификатор шаблона, к которому относится версия |
| `minor_version` | `int` | `NOT NULL` (через `PK`) | `PK`, `CHECK (minor_version >= 0)` | Целочисленный номер редакции (`0` для `1.0`, `1` для `1.1`, `10` для `1.10`) |
| `created_at` | `timestamptz` | `NOT NULL` | `DEFAULT current_timestamp` | Время сохранения данной версии в UTC |
| `title` | `text` | `NOT NULL` | — | Название шаблона на момент загрузки версии |
| `change_note` | `text` | `NULL` | — | Необязательный комментарий к изменениям |
| `file_name` | `text` | `NOT NULL` | — | Исходное имя загруженного файла (например, `Уведомление.ott`) |
| `file_format` | `varchar(3)` | `NOT NULL` | `CHECK (file_format IN ('odt', 'ott'))` | Формат файла, определённый парсером |
| `size_in_bytes` | `int` | `NOT NULL` | `CHECK (size_in_bytes BETWEEN 1 AND 20971520)` | Размер файла в байтах (не пустой, максимум 20 МиБ) |
| `file_sha256` | `varchar(64)` | `NOT NULL` | `CHECK (file_sha256 ~ '^[0-9A-Fa-f]{64}$')` | SHA-256 хеш содержимого файла (64 hex-символа) |
| `path_to_file` | `text` | `NOT NULL` | `UNIQUE` | Относительный путь к бинарному файлу в каталоге сервиса |
| `page_format` | `text` | `NOT NULL` | `DEFAULT 'A4'` | Формат страницы документа |
| `orientation` | `varchar(10)` | `NOT NULL` | `DEFAULT 'portrait'`, `CHECK (orientation IN ('portrait', 'landscape'))` | Ориентация страницы |
| `document_text` | `text` | `NOT NULL` | — | Полный извлечённый текст документа из парсера |
| `fields` | `jsonb` | `NOT NULL` | `DEFAULT '[]'::jsonb`, `CHECK (jsonb_typeof(fields) = 'array')` | JSON-массив описаний полей шаблона |

* **Первичный ключ:** составной ключ `PRIMARY KEY (template_id, minor_version)` — однозначно находит конкретную версию шаблона.
* **Внешние ключи:** `FOREIGN KEY (template_id) REFERENCES templates(template_id) ON DELETE RESTRICT` — связывает версию с родительским шаблоном и запрещает удаление шаблона, пока у него есть версии.
* **Ограничения уникальности:**
  1. `PRIMARY KEY (template_id, minor_version)` — исключает появление двух версий с одинаковым номером у одного шаблона.
  2. `UNIQUE (path_to_file)` — гарантирует, что разные версии никогда не перезапишут один и тот же файл на диске.
  

### 2.3. Индексы и их назначение

1. **`templates_pkey` (B-Tree по `templates.template_id`)** — создаётся автоматически для первичного ключа. Используется для быстрой проверки существования шаблона при `POST /api/v1/templates` и `GET /api/v1/templates/{template_id}`.
2. **`template_versions_pkey` (составной B-Tree по `template_versions(template_id, minor_version)`)** — создаётся автоматически для составного `PK`. Решает сразу три задачи:
   * точечный поиск версии по `template_id` и `minor_version`;
   * выборка истории всех версий шаблона по возрастанию или убыванию (`ORDER BY minor_version DESC`) без дополнительной сортировки в памяти;
   * быстрое нахождение актуальной версии (`MAX(minor_version)`).
3. **`template_versions_path_to_file_key` (уникальный B-Tree по `path_to_file`)** — создаётся автоматически для ограничения `UNIQUE`, гарантирует уникальность путей к файлам и не дает разным версиям шаблона ссылаться на один и тот же файл.
4. **`idx_templates_id_trgm` и `idx_template_versions_title_trgm` (GIN-индексы с `pg_trgm`)** — используются в `GET /api/v1/templates` для быстрого поиска по части строки без учета регистра (`ILIKE '%q%'`) по идентификатору шаблона и названию его актуальной версии.

## 3. REST API

Все маршруты начинаются с `/api/v1`. В примерах один шаблон `notice` имеет две версии, `1.0` и `1.1`. Обе загружены из файла с исходным именем `Уведомление.ott`. Размеры и контрольные суммы в примерах условные.

### 3.0. Общие правила

#### Данные для примеров

Во всех примерах документа используются одни и те же данные.

| | Версия 1.0 | Версия 1.1 |
|---|---|---|
| `created_at` | `2026-11-14T09:00:00Z` | `2026-11-14T10:00:00Z` |
| `title` | Уведомление | Уведомление о собрании |
| `change_note` | `null` | Добавлено поле DATE |
| `file_name` | Уведомление.ott | Уведомление.ott |
| `size_bytes` | 15643 | 17540 |
| `checksum` | `b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9` | `2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824` |
| `page` | A4, portrait | A4, landscape |
| `fields` | NAME | NAME, DATE |
| `path_to_file` | `notice/0.ott` | `notice/1.ott` |

#### Даты и ошибки

Даты передаются в UTC в формате ISO 8601: `2026-11-14T09:00:00Z`.

Ошибки, которые проверяет сам сервис (400, 404, 409, 413 и 422 для расширения и пустого файла), возвращаются с текстом:

```json
{"detail": "Шаблон unknown не найден"}
```

Ошибку 422 формирует FastAPI, когда параметр не прошел проверку. В ней список ошибок, `loc` показывает, где ошибка, `msg` - в чем она:

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "file"],
      "msg": "Field required"
    }
  ]
}
```

#### Идентификатор шаблона

`template_id` состоит из латинских букв в нижнем регистре, цифр, `_` и `-`, длина от 1 до 64 символов: `^[a-z0-9_-]{1,64}$`. Например, `notice` или `order-2026`.

Идентификатор входит в адрес запроса и в путь к файлу. Поэтому в нём нет пробелов, кириллицы и `/`.

#### Номер версии 

В API номер версии передаётся строкой `M.N`, числа без ведущих нулей: `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$`. В базе хранится только `N` в столбце `minor_version`: версия `1.10` — это `minor_version = 10`.
 
| Строка в адресе | Ответ | Почему |
|---|---|---|
| `1.0`, `1.10` | ищем версию | правильный формат |
| `1`, `1.01`, `abc` | `422` | неверный формат. `1.01` запрещён, иначе у версии `1.1` было бы два адреса |
| `2.0` | `404` | формат верный, но у сервиса бывают только версии `1.N` |

#### Параметры страницы `page` 

| Поле | Значения | По умолчанию |
|---|---|---|
| `format` | `A3`, `A4`, `A5` | `A4` |
| `orientation` | `portrait`, `landscape` | `portrait` |

#### Поле шаблона, элемент `fields`

| Поле | Тип | Описание |
|---|---|---|
| `name` | строка | имя поля без скобок: `{NAME}` в файле превращается в `NAME` |
| `type` | строка | `text`, `date` или `number` |
| `required` | логическое | обязательно ли заполнять поле при генерации документа |

Пример: `{"name": "DATE", "type": "date", "required": true}`.

#### Описание версии 

Этот объект целиком возвращается при запросе версии (3.4), лежит в карточке шаблона в поле `descriptor` (3.3) и вместе с `saved: true` возвращается после загрузки (3.1).

| Поле ответа | Откуда | Тип |
|---|---|---|
| `template_id` | `template_id` | строка |
| `version` | `"1." + minor_version` | строка |
| `title` | `title` | строка |
| `kind` | в БД не хранится, сейчас всегда `"simple"` | строка |
| `created_at` | `created_at` | дата UTC |
| `source_format` | `file_format` | `ott` или `odt` |
| `checksum` | `file_sha256` | строка из 64 символов |
| `size_bytes` | `size_in_bytes` | число |
| `page` | `page_format`, `orientation` | объект |
| `fields` | `fields` | массив |
| `change_note` | `change_note` | строка или `null` |

Извлечённый текст `document_text` в ответы не входит: он бывает большим и нужен для будущего сравнения версий.

Пример описания версии 1.1:

```json
{
  "template_id": "notice",
  "version": "1.1",
  "title": "Уведомление о собрании",
  "kind": "simple",
  "created_at": "2026-11-14T10:00:00Z",
  "source_format": "ott",
  "checksum": "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824",
  "size_bytes": 17540,
  "page": {"format": "A4", "orientation": "landscape"},
  "fields": [
    {"name": "NAME", "type": "text", "required": true},
    {"name": "DATE", "type": "date", "required": true}
  ],
  "change_note": "Добавлено поле DATE"
}
```

### 3.1. Загрузить шаблон или новую версию

`POST /api/v1/templates`

Один эндпоинт обслуживает два случая. Если `template_id` ещё нет, создаются шаблон и версия `1.0`. Если шаблон есть, добавляется следующая версия. Метод POST, потому что номер новой версии назначает сервер и клиент заранее не знает её адреса, а каждый повторный запрос создаёт ещё одну версию.

#### 1. Параметры

Параметров пути и query нет. Всё передаётся в теле `multipart/form-data`, потому что вместе с текстовыми полями передаётся файл.

```bash
curl -i -X POST localhost:8000/api/v1/templates \
  -F "template_id=notice" \
  -F "file=@Уведомление.ott" \
  -F "title=Уведомление о собрании" \
  -F "change_note=Добавлено поле DATE" \
  -F "orientation=landscape"
```

#### 2. Поля и ограничения

| Поле | Обязательное | Тип | Ограничения | Если не передано |
|---|---|---|---|---|
| `template_id` | да | строка | правило из раздела 3.0 | 422 |
| `file` | да | файл | `.ott` или `.odt`, от 1 байта до 20 МиБ (20 971 520 байт) | 422 |
| `title` | нет | строка | 1–200 символов | первая версия: имя файла без расширения; следующие: название предыдущей версии |
| `change_note` | нет | строка | 1–1000 символов | `null` |
| `page_format` | нет | строка | `A3`, `A4`, `A5` | `A4` |
| `orientation` | нет | строка | `portrait`, `landscape` | `portrait` |

Пустые строки в `title` и `change_note` сервис считает непереданными.

#### 3. Успех: `201 Created`

На сервере появилась новая версия, поэтому ответ 201, а адрес версии передаётся в заголовке `Location`.

```http
HTTP/1.1 201 Created
Location: /api/v1/templates/notice/versions/1.1
Content-Type: application/json
```

Тело — описание версии из раздела 3.0 и `saved: true`:

```json
{
  "template_id": "notice",
  "version": "1.1",
  "title": "Уведомление о собрании",
  "kind": "simple",
  "created_at": "2026-11-14T10:00:00Z",
  "source_format": "ott",
  "checksum": "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824",
  "size_bytes": 17540,
  "page": {"format": "A4", "orientation": "landscape"},
  "fields": [
    {"name": "NAME", "type": "text", "required": true},
    {"name": "DATE", "type": "date", "required": true}
  ],
  "change_note": "Добавлено поле DATE",
  "saved": true
}
```

#### 4. Ошибки

| Код | Когда | Пример ответа |
|---|---|---|
| `400 Bad Request` | парсер не смог прочитать файл: он повреждён или внутри не документ OpenDocument | `{"detail": "Не удалось прочитать файл"}` |
| `409 Conflict` | две загрузки в один шаблон одновременно получили один номер | `{"detail": "Версия 1.2 шаблона notice уже создана другим запросом, повторите загрузку"}` |
| `413 Content Too Large` | файл больше 20 МиБ | `{"detail": "Размер файла превышает 20 МиБ"}` |
| `422 Unprocessable Content` | нет `template_id` или `file` | список FastAPI, `loc: ["body", "file"]`, `type: "missing"` |
| `422 Unprocessable Content` | `template_id` не подходит под правило, например `Моё уведомление` | список FastAPI, `loc: ["body", "template_id"]` |
| `422 Unprocessable Content` | неверный `orientation` или `page_format`, например `horizontal` | список FastAPI, `loc: ["body", "orientation"]` |
| `422 Unprocessable Content` | расширение не `.ott` и не `.odt`, например `.docx` | `{"detail": "Допустимы только файлы .ott и .odt"}` |
| `422 Unprocessable Content` | файл пустой | `{"detail": "Файл пустой"}` |

422 означает, что неверны сами параметры, и это видно до чтения содержимого. 400 означает, что параметры верны, но содержимое файла прочитать нельзя, например картинку переименовали в `.ott`.

409 возникает, когда два запроса одновременно прочитали последний номер `1.1` и оба решили создать `1.2`. Первый запрос вставил строку, второй упёрся в первичный ключ `(template_id, minor_version)`.

#### 5. Работа с БД и файлами

Порядок действий:

1. Проверить поля формы и расширение файла. При ошибке ответить 422.
2. Прочитать файл, но не больше 20 МиБ и 1 байта. Больше — 413, пустой — 422.
3. Передать байты и имя файла парсеру. Если он отказал, ответить 400. На диске и в базе ничего не появляется.
4. Прочитать `max(minor_version)` в `template_versions` по `template_id`. Строк нет — номер 0, иначе максимум плюс 1.
5. Записать файл на диск по пути `{template_id}/{minor_version}.{file_format}`, например `notice/1.ott`.
6. В одной транзакции выполнить `insert into templates ... on conflict do nothing` и вставить строку в `template_versions`.
7. Если транзакция не прошла, удалить файл из шага 5. Ошибка первичного ключа даёт 409.

Парсер вызывается раньше записи на диск и в базу, поэтому отклонённый файл нигде не оставляет следов, а прежняя актуальная версия остаётся доступной.

Шаблон и его первая версия создаются в одной транзакции, потому что шаблон без версий в каталоге существовать не должен.

`on conflict do nothing` нужен, когда две первые загрузки нового шаблона приходят одновременно: второй запрос не должен упасть на вставке строки в `templates`.

Путь к файлу строится из `template_id` и номера, а не из имени файла. Имена файлов у разных шаблонов могут совпадать, в них бывает кириллица и `../`. Пара `template_id` и номер уникальна, и `unique (path_to_file)` это подтверждает.

Прочитано: `templates` (есть ли шаблон), `template_versions` (последний номер). Создано: строка в `templates` при первой загрузке, строка в `template_versions`, файл на диске.

### 3.2. Получить каталог шаблонов

`GET /api/v1/templates`

Возвращает страницу шаблонов с поиском. Метод GET, потому что запрос только читает данные. Поиск передаётся в query: ресурс тот же самый, каталог, только отфильтрованный.

#### 1. Параметры

Все параметры в query, тела нет:

```text
GET /api/v1/templates?q=увед&limit=20&offset=0
```

#### 2. Типы и ограничения

| Параметр | Тип | Ограничения | По умолчанию | Назначение |
|---|---|---|---|---|
| `q` | строка | до 100 символов | не задан, выводятся все шаблоны | поиск по части `template_id` или названия актуальной версии без учёта регистра |
| `limit` | целое | 1–100 | 20 | сколько шаблонов вернуть |
| `offset` | целое | от 0 | 0 | сколько шаблонов пропустить |

Шаблоны сортируются по `template_id` по возрастанию. Без постоянного порядка база может отдавать строки по-разному, и при переходе между страницами шаблоны будут повторяться или пропадать.

Поиск идёт по названию актуальной версии, потому что в каталоге пользователь видит только его.

#### 3. Успех: `200 OK`

```json
{
  "total": 1,
  "items": [
    {
      "template_id": "notice",
      "title": "Уведомление о собрании",
      "latest_version": "1.1",
      "versions_count": 2,
      "updated_at": "2026-11-14T10:00:00Z"
    }
  ]
}
```

| Поле | Откуда |
|---|---|
| `total` | сколько шаблонов подходит под `q` до применения `limit` и `offset` |
| `template_id` | `templates.template_id` |
| `title` | `title` версии с наибольшим `minor_version` |
| `latest_version` | `"1." + max(minor_version)` |
| `versions_count` | количество версий шаблона |
| `updated_at` | `created_at` последней версии, то есть время последней загрузки |

#### 4. Ошибки

| Код | Когда | Пример ответа |
|---|---|---|
| `422 Unprocessable Content` | `limit=0`, `limit=500`, `offset=-1`, `limit=abc` | список FastAPI, `loc: ["query", "limit"]` |

Если ничего не найдено, ответ `200 OK` и `{"total": 0, "items": []}`: каталог существует, просто в нём нет совпадений. Если `offset` больше числа совпадений, `items` пустой, а `total` показывает число совпадений.

#### 5. Работа с БД

Только чтение `templates` и `template_versions`:

1. Для каждого шаблона найти последнюю версию и посчитать количество версий.
2. Отобрать шаблоны, у которых `template_id` или название последней версии содержит `q`.
3. Посчитать `total`.
4. Применить `order by template_id`, `limit` и `offset`.

Для поиска по части строки используются GIN-индексы с `pg_trgm` из раздела 2.3.

### 3.3. Получить карточку шаблона

`GET /api/v1/templates/{template_id}`

Возвращает шаблон целиком: актуальное название, историю версий и полное описание актуальной версии. Клиенту не нужен второй запрос, чтобы показать страницу шаблона.

#### 1. Параметры

`template_id` в пути, query и тела нет:

```text
GET /api/v1/templates/notice
```

#### 2. Типы и ограничения

`template_id` — обязательная строка по правилу из раздела 3.0.

#### 3. Успех: `200 OK`

```json
{
  "template_id": "notice",
  "title": "Уведомление о собрании",
  "latest_version": "1.1",
  "versions": [
    {
      "version": "1.1",
      "title": "Уведомление о собрании",
      "created_at": "2026-11-14T10:00:00Z",
      "change_note": "Добавлено поле DATE"
    },
    {
      "version": "1.0",
      "title": "Уведомление",
      "created_at": "2026-11-14T09:00:00Z",
      "change_note": null
    }
  ],
  "descriptor": {
    "template_id": "notice",
    "version": "1.1",
    "title": "Уведомление о собрании",
    "kind": "simple",
    "created_at": "2026-11-14T10:00:00Z",
    "source_format": "ott",
    "checksum": "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824",
    "size_bytes": 17540,
    "page": {"format": "A4", "orientation": "landscape"},
    "fields": [
      {"name": "NAME", "type": "text", "required": true},
      {"name": "DATE", "type": "date", "required": true}
    ],
    "change_note": "Добавлено поле DATE"
  }
}
```

`versions` — история от новой версии к старой. Для каждой версии указано, когда она загружена и что изменилось. Полное описание любой версии доступно в разделе 3.4, поэтому `fields` и `checksum` в историю не входят.

`descriptor` — описание актуальной версии в формате из раздела 3.0.

#### 4. Ошибки

| Код | Когда | Пример ответа |
|---|---|---|
| `404 Not Found` | шаблона нет | `{"detail": "Шаблон unknown не найден"}` |
| `422 Unprocessable Content` | `template_id` не подходит под правило | список FastAPI, `loc: ["path", "template_id"]` |

#### 5. Работа с БД

Только чтение:

1. Найти шаблон в `templates`. Нет — 404.
2. Прочитать все версии из `template_versions` с сортировкой `minor_version desc`. Порядок даёт индекс первичного ключа.
3. Первая строка — актуальная версия. Из неё берутся `title`, `latest_version` и `descriptor`.
4. Из всех строк собирается `versions`.

### 3.4. Получить описание конкретной версии

`GET /api/v1/templates/{template_id}/versions/{version}`

Возвращает описание одной версии, в том числе старой. Адрес вложенный, потому что версия не существует без шаблона, а её номер уникален только внутри шаблона: версия `1.0` может быть и у `notice`, и у `order`. Адрес повторяет первичный ключ `(template_id, minor_version)`.

#### 1. Параметры

`template_id` и `version` в пути, query и тела нет:

```text
GET /api/v1/templates/notice/versions/1.0
```

#### 2. Типы и ограничения

`template_id` и `version` — обязательные строки по правилам из раздела 3.0.

#### 3. Успех: `200 OK`

Тело — описание версии из раздела 3.0:

```json
{
  "template_id": "notice",
  "version": "1.0",
  "title": "Уведомление",
  "kind": "simple",
  "created_at": "2026-11-14T09:00:00Z",
  "source_format": "ott",
  "checksum": "b94d27b9934d3e08a52e52d7da7dabfac484efe37a5380ee9088f7ace2efcde9",
  "size_bytes": 15643,
  "page": {"format": "A4", "orientation": "portrait"},
  "fields": [
    {"name": "NAME", "type": "text", "required": true}
  ],
  "change_note": null
}
```

#### 4. Ошибки

| Код | Когда | Пример ответа |
|---|---|---|
| `404 Not Found` | нет шаблона | `{"detail": "Шаблон unknown не найден"}` |
| `404 Not Found` | шаблон есть, версии нет, например `1.5` или `2.0` | `{"detail": "Версия 1.5 шаблона notice не найдена"}` |
| `422 Unprocessable Content` | номер не по формату: `1`, `1.01`, `abc` | список FastAPI, `loc: ["path", "version"]` |

Сначала проверяется шаблон, потом версия. Иначе на запрос `unknown/versions/1.0` пришло бы «версия не найдена», хотя нет самого шаблона.

#### 5. Работа с БД

Только чтение:

1. Разобрать номер: `1.0` даёт `minor_version = 0`. Если первое число не `1`, ответить 404.
2. Найти шаблон в `templates`. Нет — 404 «шаблон не найден».
3. Найти строку в `template_versions` по `(template_id, minor_version)`. Нет — 404 «версия не найдена».
4. Собрать ответ по таблице соответствия из раздела 3.0.

### 3.5. Скачать файл конкретной версии

`GET /api/v1/templates/{template_id}/versions/{version}/file`

Возвращает байты файла, а не JSON. Скачивание вынесено в отдельный адрес: описание версии весит несколько килобайт, а файл до 20 МиБ, и клиенту, которому нужно только описание, незачем скачивать файл.

#### 1. Параметры

Как в разделе 3.4:

```text
GET /api/v1/templates/notice/versions/1.0/file
```

#### 2. Типы и ограничения

Те же правила для `template_id` и `version` из раздела 3.0.

#### 3. Успех: `200 OK`

Тело — байты файла. Заголовки:

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.oasis.opendocument.text-template
Content-Length: 15643
Content-Disposition: attachment; filename="notice-1.0.ott"; filename*=UTF-8''%D0%A3%D0%B2%D0%B5%D0%B4%D0%BE%D0%BC%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5.ott
```

`Content-Type` выбирается по `file_format`:

| `file_format` | `Content-Type` |
|---|---|
| `ott` | `application/vnd.oasis.opendocument.text-template` |
| `odt` | `application/vnd.oasis.opendocument.text` |

`Content-Length` берётся из `size_in_bytes`.

Имя файла клиент узнаёт из заголовка `Content-Disposition`:
- `attachment` — сохранить как файл, а не открыть в браузере;
- `filename*` — исходное имя `Уведомление.ott` из `file_name`. Заголовки HTTP передаются латиницей, поэтому кириллица закодирована;
- `filename` — запасное имя латиницей для клиентов, которые не понимают `filename*`. Собирается из `template_id` и номера версии.

#### 4. Ошибки

| Код | Когда | Пример ответа |
|---|---|---|
| `404 Not Found` | нет шаблона | `{"detail": "Шаблон unknown не найден"}` |
| `404 Not Found` | нет версии | `{"detail": "Версия 1.5 шаблона notice не найдена"}` |
| `422 Unprocessable Content` | номер не по формату | список FastAPI, `loc: ["path", "version"]` |

Ошибки приходят в JSON с заголовком `Content-Type: application/json`, хотя успешный ответ — файл.

Если строка версии в базе есть, а файла на диске нет, это поломка сервера, и ответ будет `500 Internal Server Error`.

#### 5. Работа с БД и файлами

1. Найти шаблон и версию, как в разделе 3.4.
2. Взять из строки версии `path_to_file`, `file_format`, `file_name` и `size_in_bytes`.
3. Открыть файл по `path_to_file` и отдать его байты с заголовками.

В базе ничего не меняется.

## 4. Проверка проекта на примерах

### Ситуация 1. Первая загрузка шаблона

**Запрос.** `POST /api/v1/templates`, `multipart/form-data`:
`template_id = notice`, `file = Уведомление.ott`, `title = Уведомление`.
`page_format` и `orientation` не переданы.

**Что делает сервис.**
1. Проверяет форму: `template_id` и файл есть, расширение `.ott`, размер 15 643 байта, это меньше 20 МиБ.
2. Парсер разбирает файл: найдено поле `NAME`, формат `ott`, SHA-256 `b94d27b9...`.
3. Шаблона `notice` в `templates` нет, значит это первая версия, `minor_version = 0`.
4. Файл записывается на диск как `notice/0.ott`.
5. В одной транзакции создаются строки в `templates` и `template_versions`.

**Ответ.** `201 Created`, заголовок `Location: /api/v1/templates/notice/versions/1.0`, в теле описание версии 1.0 и `"saved": true`.

**База данных.**
- Прочитано: `templates`, строки `notice` нет; `template_versions`, версий у `notice` нет.
- Создано в `templates`: `template_id = notice`, `created_at = 2026-11-14 09:00:00 UTC`.
- Создано в `template_versions`: `template_id = notice`, `minor_version = 0`, `title = Уведомление`, `file_name = Уведомление.ott`, `file_format = ott`, `size_in_bytes = 15643`, `path_to_file = notice/0.ott`, `page_format = A4`, `orientation = portrait`, `change_note = null`.

**Диск.** Появился файл `notice/0.ott`.

### Ситуация 2. Загрузили исправленный файл под тем же `template_id`

**Запрос.** `POST /api/v1/templates`, `multipart/form-data`:
`template_id = notice`, `file = Уведомление.ott` (исправленный, добавлено поле `{DATE}`), `title = Уведомление о собрании`, `change_note = Добавлено поле DATE`, `orientation = landscape`.

**Что делает сервис.**
1. Форма в порядке, файл весит 17 540 байт.
2. Парсер находит поля `NAME` и `DATE` и считает SHA-256 `2cf24dba...`. Хеш отличается от версии 1.0, потому что поменялось содержимое файла.
3. Шаблон `notice` уже есть, поэтому новую строку в `templates` сервис не создаёт.
4. Последний номер у `notice` равен 0, значит новая версия получает `minor_version = 1`, то есть `1.1`.
5. Файл сохраняется как `notice/1.ott`. Старый `notice/0.ott` не трогается.

**Ответ.** `201 Created`, `Location: /api/v1/templates/notice/versions/1.1`, в теле описание версии 1.1 и `"saved": true`, как в примере раздела 3.1.

**База данных.**
- Прочитано: `templates` (шаблон `notice` есть), `template_versions` (последний номер 0).
- Создано в `template_versions`: `template_id = notice`, `minor_version = 1`, `title = Уведомление о собрании`, `change_note = Добавлено поле DATE`, `size_in_bytes = 17540`, `path_to_file = notice/1.ott`, `orientation = landscape`, `created_at = 2026-11-14 10:00:00 UTC`.
- В `templates` ничего не изменилось. Строка версии 1.0 осталась как была.

**Диск.** Появился `notice/1.ott`, рядом лежит прежний `notice/0.ott`.

**Проверка, что старая версия доступна.** `GET /api/v1/templates/notice/versions/1.0/file` отвечает `200 OK` и отдаёт файл `notice/0.ott` с `Content-Length: 15643`. Новая загрузка ничего не перезаписала.

### Ситуация 3. Тот же файл загрузили под другим `template_id`

**Запрос.** `POST /api/v1/templates`, `multipart/form-data`:
`template_id = order`, `file = Уведомление.ott` (тот же файл, что у `notice` версии 1.0), `title = Приказ`.

**Что делает сервис.**
1. Форма в порядке, размер 15 643 байта.
2. Парсер возвращает то же, что для `notice` 1.0: поле `NAME`, SHA-256 `b94d27b9...`.
3. Шаблона `order` нет, значит это новый шаблон и его первая версия, `minor_version = 0`.
4. Файл сохраняется как `order/0.ott`.

**Ответ.** `201 Created`, `Location: /api/v1/templates/order/versions/1.0`.

**База данных.**
- Создано в `templates`: `template_id = order`.
- Создано в `template_versions`: `template_id = order`, `minor_version = 0`, `title = Приказ`, `file_name = Уведомление.ott`, `size_in_bytes = 15643`, `file_sha256 = b94d27b9...`, `path_to_file = order/0.ott`.
- Строки шаблона `notice` не изменились.

**Диск.** Появился `order/0.ott`. Файл `notice/0.ott` не перезаписан, потому что путь строится из `template_id`, а не из имени файла.

**Почему это отдельный шаблон.** Шаблоны различаются по `template_id`. У `order` и `notice` 1.0 совпадают имя файла и SHA-256, но это просто описание файла: одно и то же содержимое можно загрузить в разные шаблоны. Теперь каталог `GET /api/v1/templates` показывает `total: 2`.

### Ситуация 4. Запросили версию, которой нет

**Запрос.** `GET /api/v1/templates/notice/versions/1.5`

**Что делает сервис.**
1. Номер `1.5` подходит под формат, это `minor_version = 5`.
2. Шаблон `notice` в `templates` есть.
3. Строки `(notice, 5)` в `template_versions` нет: у шаблона только версии 0 и 1.

**Ответ.** `404 Not Found`, `{"detail": "Версия 1.5 шаблона notice не найдена"}`.

**База данных.** Только чтение, ничего не создано.

Если запросить версию у несуществующего шаблона, `GET /api/v1/templates/unknown/versions/1.0`, ответ тоже 404, но с текстом `{"detail": "Шаблон unknown не найден"}`: сервис сначала ищет шаблон и дальше не идёт.

### Ситуация 5. Парсер не принял файл

**Запрос.** `POST /api/v1/templates`, `multipart/form-data`:
`template_id = notice`, `file = Уведомление.ott`. На самом деле это картинка, у которой поменяли расширение на `.ott`.

**Что делает сервис.**
1. Форма в порядке: `template_id` есть, расширение `.ott`, размер меньше 20 МиБ.
2. Парсер не может прочитать файл, потому что внутри не документ OpenDocument.
3. Сервис сразу отвечает ошибкой. До записи на диск и в базу дело не доходит.

**Ответ.** `400 Bad Request`, `{"detail": "Не удалось прочитать файл"}`.

**База данных.** Ничего не создано. Номер `minor_version = 2` не занят, его получит следующая успешная загрузка.

**Диск.** Ничего не записано.

**Проверка, что прежняя версия осталась актуальной.** `GET /api/v1/templates/notice` возвращает `latest_version: "1.1"`, в `versions` по-прежнему две записи. Неудачная загрузка ни на что не повлияла, потому что парсер вызывается раньше, чем сервис что-то сохраняет.

## 5. Почему сделано так

**Как определяется актуальная версия.** Актуальная та, у которой самый большой `minor_version`. Отдельно её нигде не храним: версии никогда не удаляются, поэтому самый большой номер и есть последняя успешная загрузка. Индекс первичного ключа находит её сразу.

**Как не допустить двух одинаковых номеров.** У таблицы `template_versions` первичный ключ из двух полей, `(template_id, minor_version)`. База не даст вставить вторую строку с той же парой. Если два запроса придут одновременно и оба выберут один номер, второй получит 409 и сможет повторить загрузку.

**Почему номер хранится числом.** Строки сравниваются по символам, и `'1.10'` получается меньше `'1.9'`. Числа сравниваются правильно: 10 больше 9. По ТЗ все версии вида `1.N`, поэтому храним только `N`. Если когда-нибудь появится `2.0`, добавим столбец `major_version`.

**Почему поля шаблона лежат в JSONB.** Поля всегда нужны вместе с версией, после загрузки не меняются и отдаются в API тем же списком. Отдельная таблица была бы полезна, если бы понадобилось искать, например, все шаблоны с полем `DATE`. Сейчас такой задачи нет.

**Почему парсер вызывается до сохранения.** Если файл плохой, сервис узнаёт об этом раньше, чем что-то запишет. Поэтому неудачная загрузка не оставляет ни строки в базе, ни файла на диске.
